# Runtime process-tree and packed-executable relaxation

## Status and scope

This document specifies the process-tree execution policy for entries that
unpack, create, or invoke additional executables while compressing or
decompressing.

The Hutter Prize size formulas and resource limits apply without modification.
This policy defines which files contribute bytes to those formulas when a
counted program expands into one or more runtime programs.

The source-ZIP-in-lieu-of-an-executable relaxation is outside the scope of this
document. For automated scoring here, `COMPRESSOR` and, when applicable,
`DECOMPRESSOR` mean the exact rebuilt executable artifact or artifact bundle.
The source package is used for reproducible rebuilding and source
correspondence, but its size is not substituted for the rebuilt executable
size.

Documentation, disclosure, source quality, licensing, attribution, platform
eligibility, and the spirit of the Prize remain matters for human judges. The
judging assistant records objective evidence and proposes a score; it does not
decide those subjective questions.

## Governing principle

The score counts the representations supplied across a judging-phase boundary,
not every file produced from those representations during execution.

For example, a packed 30,000-byte program may write a 1,000,000-byte executable
and invoke it. The score includes the 30,000-byte packed representation once.
The expanded executable is a temporary product of an already-counted program,
so adding another 1,000,000 bytes would count the same encoded information
twice.

The expanded file still consumes temporary disk, and its process still consumes
CPU time, elapsed time, and memory. Size accounting and resource accounting are
separate.

```text
counted phase input
        |
        +-- unpack or generate runtime executable -- not scored again
        +-- create temporary files                -- not scored
        +-- run descendants                        -- same resource limits
        |
        `-- produce declared phase output          -- counted by the formula
```

## Definitions

**Phase boundary**
: The point at which the judging orchestrator places declared artifacts and
  inputs into a new execution environment before starting entrant code.

**Independently staged artifact**
: A file supplied by the orchestrator at a phase boundary. Its bytes are not a
  runtime product of another artifact in that phase.

**Artifact bundle**
: All independently staged entrant executable or auxiliary files required for
  one declared role. If more than one such file is supplied, the bundle size is
  the sum of their exact file sizes. A bundle does not include files generated
  after the role starts.

**Runtime product**
: A file created after the declared role starts from the information available
  inside that phase. Examples include an unpacked executable, a copied
  self-image, generated code, a dictionary reconstructed by a program, and an
  intermediate data file.

**Process tree**
: The initial declared program and every descendant created by `fork`, `vfork`,
  `clone`, `execve`, `execveat`, or an equivalent platform operation. Replacing
  a process image or invoking a child does not start a new resource allowance.

## Permitted execution

A declared compressor, self-extracting archive, or separate decompressor MAY:

- execute itself again with different arguments;
- unpack or generate an executable in its working directory and execute it;
- invoke a packed wrapper target, preprocessor, compressor, postprocessor, or
  decompressor encoded by a counted artifact;
- use multiple sequential or concurrent descendant processes; and
- use the platform runtime and standard libraries available in the declared
  judging environment.

All descendants MUST remain in the original container, security boundary,
process-tracking domain, and resource-control group. Descendant execution MUST
NOT provide access to the network, the host filesystem, the reference corpus
during decompression, another entry, or an undeclared entrant data file.

Platform programs used merely as runtime or launch machinery, such as a dynamic
loader or command interpreter, are not entrant artifacts. They MUST NOT be used
as unaccounted algorithmic compressors, preprocessors, dictionaries, models, or
other sources of benchmark-relevant information. The judging assistant SHOULD
record descendant executable paths and digests where practicable so human
judges can review this distinction.

## Size accounting

Let:

- `C` be the rebuilt compressor artifact bundle;
- `A` be the exact archive generated by the rebuilt compressor;
- `D` be the rebuilt separate-decompressor artifact bundle, when applicable;
- `CA` be the declared compressor-argument bytes;
- `DA` be the declared decompressor-argument bytes; and
- `m` be the applicable separate-decompressor multiplier.

For a self-extracting entry, the proposed score remains:

```text
S = bytes(C) + bytes(A) + bytes(CA)
```

For a separate-decompressor entry, the proposed Relaxations score remains:

```text
S = bytes(C) + m * bytes(D) + bytes(A) + bytes(CA) + bytes(DA)
```

The multiplier `m` is 2, reduced to 1 only when the rebuilt compressor and
decompressor bundles satisfy the official identity condition. The judging
assistant MUST retain exact sizes and digests so a human judge can review that
condition.

The following rules apply to both formulas:

1. Every independently staged entrant artifact belongs to a declared bundle
   and contributes its exact size to that bundle.
2. A runtime product is not added to `S`, even when it is executable or much
   larger than the artifact that created it.
3. Bytes already contained in `C`, `D`, or `A` are counted once, in that
   representation, and are not counted again after extraction.
4. An independently supplied helper that is not encoded or generated by an
   already-counted phase input MUST be declared and included in the applicable
   artifact bundle.
5. Generated archive bytes are counted as `A` even when the archive later
   expands into one or more decompression executables.
6. Temporary-file sizes affect the disk limit, not `S`.

### Examples

```text
Packed compressor C (30 KB)
  -> writes compressor helper H (1 MB)
  -> executes H

Compressor contribution to S: 30 KB
Temporary-disk contribution:   includes H's allocated disk space
```

```text
Compressor C (30 KB) and independently staged helper H (1 MB)
  -> C executes H

Compressor contribution to S: 30 KB + 1 MB
```

```text
Self-extracting archive A
  -> writes decompressor Dtmp
  -> executes Dtmp
  -> produces enwik9

Archive contribution to S: bytes(A), with no additional charge for Dtmp
```

```text
Separately declared packed decompressor D
  -> writes and executes a larger decompressor Dtmp

Decompressor contribution to S: m * bytes(D), not m * bytes(Dtmp)
```

## Resource accounting

The entire process tree is one logical invocation. Allowing descendants does
not grant additional resources.

- CPU capacity is limited to one core in aggregate across the process tree.
- Wall time starts when the declared root program is invoked and ends only
  after the tracked process tree has terminated.
- The 10 GiB memory limit applies to aggregate resident memory of the process
  tree. A conforming implementation SHOULD obtain the peak from the execution
  cgroup, rather than assuming one process's maximum RSS represents concurrent
  descendants.
- The execution environment remains fixed at 16 GiB with no swap.
- The 100 GB temporary-disk limit applies to all files created by the process
  tree, including unpacked executables.
- A timeout or resource violation terminates the complete process tree.
- Network and privilege restrictions apply to every descendant.

## Phase closure and outside information

At the compression boundary, entrant code receives only its counted compressor
bundle, declared arguments, the reference `enwik9`, and the documented platform
runtime. At the decompression boundary, entrant code receives only the counted
self-extracting archive, or the counted separate-decompressor bundle plus its
declared archive data and arguments, and the documented platform runtime.

After a phase begins, an executable reconstructed from those inputs introduces
no new outside information. An `execve` boundary is therefore not, by itself, a
score boundary. Conversely, placing an additional pre-existing entrant helper
in the phase introduces independently supplied information and requires that
helper to be declared and counted.

The orchestrator MUST record the exact initially staged files, sizes, and
digests. It MUST NOT silently add compatibility executables, entrant-specific
tools, dictionaries, models, or other build products to a runtime phase.

## Judging-assistant behavior

The `--runtime-exec-policy process-tree` option selects the execution policy
specified here. Qualification under this policy requires aggregate resource
accounting and complete phase-boundary evidence as specified above.

The strict policy MAY be used as a diagnostic option. Failure under the strict
policy alone is not evidence that an entry violates this relaxation.

Reports SHOULD distinguish at least:

- the declared root invocation;
- runtime self-extraction or executable unpacking;
- preprocessing and postprocessing descendants;
- the principal compression or decompression operation;
- descendant exit status or terminating signal;
- the declared output's size and digest; and
- aggregate CPU, elapsed-time, memory, and disk evidence.

This distinction is necessary because a failure while unpacking a runtime
helper is not the same event as a failure while compressing `enwik9`.

## Justification

The official Hutter Prize measures description length: compressor plus archive
for the self-extracting form, or the applicable compressor, decompressor, and
archive terms under the Relaxations. The official rules also permit compressed
executables, and the official FAQ specifically identifies executable packing
as a way to produce smaller self-contained programs:

- <https://www.hutter1.net/prize/hrules.htm>
- <https://www.hutter1.net/prize/hfaq.htm>

Historically, packed entries have expanded an executable onto disk and invoked
that executable for compression or decompression. Charging the packed input and
the expanded runtime image would penalize the act of decoding program bytes and
would make the score depend on whether unpacking ends with a jump, an in-memory
loader, or an `execve`. Those mechanisms can represent the same encoded program
and should have the same size score.

A rule based solely on later executable invocation would require multi-stage
`cmix` entries to be substantially rewritten. Such a rewrite can change
executable and archive sizes, performance, memory behavior, and failure modes
without changing the submitted compression idea, reducing comparability among
results.

This relaxation places the boundary where the benchmark needs it:

- independently supplied information is declared and counted;
- decoded or generated runtime representations are not double-counted;
- all computation remains confined and fully resource-limited; and
- subjective compliance remains reviewable by human judges.
